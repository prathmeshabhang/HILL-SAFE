# FLOODY SHIELD v3.4 — Authentication, RBAC & Life-Safety Security Specification

**System**: FLOODY SHIELD (Predict • Protect • Preserve)  
**Target Basin**: Upper Beas River Basin — Kullu–Manali, Himachal Pradesh, India  
**Scope**: Cryptographic Auth, Role Hierarchy, Commander Authorization Gateway, WebSocket Restrictions  

---

## 1. Authentication Architecture

FLOODY SHIELD v3.4 enforces defense-in-depth access controls designed specifically for critical national emergency infrastructure.

### 1.1 Password Hashing
- Algorithm: **bcrypt** (`bcrypt.gensalt()` with work factor 12).
- Truncation: Standard 72-byte password length boundary enforced.
- Never stores plaintext credentials in memory or database records.

### 1.2 JWT Bearer Tokens
- Algorithm: **HS256** (HMAC with SHA-256).
- Standard Claims:
  - `sub`: Unique user identifier / username.
  - `role`: Role string (`OBSERVER`, `ANALYST`, `SENIOR_INCIDENT_COMMANDER`).
  - `jti`: Unique token UUID preventing token replay.
  - `exp`: Expiration timestamp (default: 60 minutes).
- Issuance: `POST /api/v1/auth/login`.

## 2. Role-Based Access Control (RBAC) Hierarchy

FLOODY SHIELD defines three statutory operating roles:

```
[ Level 3: SENIOR_INCIDENT_COMMANDER ]
  * Has all permissions of ANALYST and OBSERVER
  * Exclusive authority to sign off on early warning alerts
  * Authorize CAP v1.2 warning dispatches
  * Cancel alerts and declare emergency escalation
                  ^
                  | (Strict Hierarchy)
[ Level 2: ANALYST ]
  * Has all permissions of OBSERVER
  * Register and calibrate physical sensors and devices
  * Trigger manual model pipeline runs
  * Create alert drafts (PENDING_APPROVAL)
  * Ingest batch external GIS and remote sensing scenes
                  ^
                  | (Strict Hierarchy)
[ Level 1: OBSERVER ]
  * Read-only access to GIS hazard maps, EOC dashboards
  * View current and historical risk states
  * Stream live telemetry and model inferences
```

## 3. Human-in-the-Loop Life-Safety Gateway

### 3.1 Statutory Invariant
**NON-NEGOTIABLE SAFETY RULE**: Under no circumstances may an artificial intelligence model, numerical physics simulation, or automated pipeline trigger or dispatch a public disaster warning independently.

- Every alert generated by the system (whether by autonomous orchestrator, threshold rule, or analyst draft) is initialized with:
  $$\text{status} = \text{"PENDING\_APPROVAL"}$$
- Public dispatch channels (sirens, cell broadcast, NDMA Sachet, SMS) remain blocked until statutory sign-off.

### 3.2 Authorization REST Gateway
To transition an alert from `PENDING_APPROVAL` to `DISPATCHED`, the authorized Incident Commander must call:
`POST /api/v1/alerts/{alert_id}/authorize`

Request Payload:
```json
{
  "actor_id": "SENIOR_COMMANDER_KULLU_01",
  "actor_role": "SENIOR_INCIDENT_COMMANDER",
  "approval_token": "CRYPTO_SIGN_OFF_AUT_2026_APPROVED"
}
```

Validation Checklist:
1. Verifies caller possesses `SENIOR_INCIDENT_COMMANDER` role in JWT claim.
2. Verifies cryptographic approval token is non-empty and valid.
3. Verifies alert is currently in `PENDING_APPROVAL` (rejects cancelled, already dispatched, or resolved alerts with HTTP 400).
4. Generates and validates statutory OASIS CAP v1.2 XML.
5. Commits to tamper-evident audit log with cryptographic hash chain.
6. Asynchronously dispatches alert via `NotificationDispatcher`.

## 4. WebSocket Authorization Prohibition

To protect against cross-site scripting (XSS), token leakage in browser contexts, or unauthorized streaming manipulation:

- **WebSockets are strictly read-only streaming channels** for subscribing to telemetry, risk states, and alert notifications.
- Any client attempting to send authorization frames over WebSocket (e.g. `{"action": "AUTHORIZE_ALERT", ...}`) is immediately rejected with:
```json
{
  "type": "SECURITY_ERROR",
  "code": "WEBSOCKET_AUTHORIZATION_PROHIBITED",
  "error": "WEBSOCKET_AUTHORIZATION_PROHIBITED",
  "message": "Life-safety emergency alert authorization cannot be executed via WebSocket. The authenticated REST API gateway (POST /api/v1/alerts/{id}/authorize) is required."
}
```
Alert authorization remains exclusively anchored to the authenticated REST gateway.
